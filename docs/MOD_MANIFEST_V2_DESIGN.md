# Mod Manifest v2 Design / Mod 元数据与兼容准入设计

> Status / 状态：设计草案，尚未实施，也不表示用户已确认全部规则。
> Date / 日期：2026-10-15。
> Scope / 范围：`mod.json`、发布清单、构建校验、安装及启动前准入、旧格式迁移。
> 当前有效格式仍见 [Mod SDK](../mod_sdk/README.md)；当前运行行为见 [Architecture](ARCHITECTURE.md) §1.11。

## 1. Problem / 问题与证据

当前 manifest 混合展示信息、兼容声明、构建选项和内容注册配置，部分字段不参与挂载前判断。

| 当前行为 | 风险与证据 |
|---|---|
| `game_version` 仅声明最低本体版本，版本不足也只告警 | 更新本体仍可能加载不兼容旧包。`script/mod_manager.gd:566,572` |
| `api_version` 超限仅跳过 entry，缺失时默认当前接口版本 | 资源已经挂载，内容扫描及补丁可能已经执行。`script/mod_manager.gd:88,1010` |
| `replace_paths` 仅供构建选择导出资源 | 运行期未验证实际覆盖清单，导出依赖可能额外带入本体文件。`mod_sdk/build_mod.ps1:24,40` |
| 安装事务校验 PCK 格式、引擎要求、数据范围与 MD5 | 不能证明脚本兼容；手动放入目录的包不经过安装事务。`script/mod_installer.gd:36`、`script/mod_pack_validator.gd:6` |
| 没有 entry 的 Mod 仍可携带脚本 | 资源扫描会加载资源，社团扫描还会实例化场景。`script/mod_manager.gd:697,725` |

已验证的事故是旧联机 PCK 携带 `script/mod_manager.gd.remap` / `.gdc`，使后加载管理页读取旧 void 返回签名，而运行期 autoload 仍使用新版实现。单纯检查 `api_version=1` 不能识别该问题。详见 [Learnings](LEARNINGS.md) 的 `[Mod/Parser]` 条目及 `tests/test_mod_option_api.py`。

Godot 的 `load_resource_pack(..., replace_files=true)` 会让同路径文件的后续加载使用包内文件，因此必须在挂载前完成检查，不能以挂载候选包作为预检手段。依据：[Godot 官方文档](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-method-load-resource-pack)。

## 2. Principles / 设计原则

- 区分 manifest 格式版本、Mod 自身版本、本体兼容范围、Mod 接口版本和本体文件契约。
- 作者声明意图，构建工具生成产物事实；加载器独立核对事实。
- 安装与启动复用同一套只读校验规则，覆盖已有安装、手动安装和便携目录。
- 检查未通过时不挂载、不加载候选资源、不执行入口或补丁。
- 不兼容不等于用户主动停用：保留安装和启用选择，单独记录拒载原因。
- `additive` / `override` 仅描述文件覆盖方式，不表示是否执行脚本，也不构成脚本沙箱。
- 第一版只提供项目需要的范围表达和依赖能力，不引入完整依赖求解器。

## 3. Files / 配置与发布文件

建议发布结构：

```text
<mod_id>.zip
  mod.json
  package.lock.json
  content_index.json
  <mod_id>.pck
  icon.png                 # 可选
```

| 文件 | 维护者与职责 |
|---|---|
| 源码中的 `mod.json` | 作者维护身份、兼容要求、入口、依赖和覆盖意图 |
| 发布目录的 `mod.json` | 构建工具校验并规范化后输出；不自动扩大兼容范围 |
| `package.lock.json` | 构建工具生成，记录该次发布的实际文件与构建信息 |
| `content_index.json` | 显式内容声明与构建生成索引的输出；使用现有索引能力逐步演进 |
| PCK | 实际资源产物，须与 manifest、发布清单一致 |
| `icon.png` | 可在拒载状态下直接展示，不需要挂载 PCK |

发布清单应覆盖包外的内容索引等功能性文件，避免只校验 PCK 而遗漏 loose 文件。现有 loose 补丁优先规则需要在迁移时明确归属，不能让未纳入发布清单的文件悄悄改变发布行为。证据：`script/mod_manager.gd:434`。

开发目录可允许未生成清单，但必须使用显式开发模式；发布包不能悄悄降级为开发模式。开发模式也不放开受保护核心文件。

## 4. Manifest / 建议结构

以下为有效 JSON 示例。版本范围仅示意，不表示该范围已经通过兼容验证。

```json
{
  "schema_version": 2,
  "id": "example",
  "version": "0.1.0",
  "name": "示例 Mod",
  "description": "增加角色与道具",
  "authors": ["作者"],
  "icon": "icon.png",
  "compatibility": {
    "game": {
      "min": "v0.5.1.4",
      "max_exclusive": "v0.5.2.0"
    },
    "mod_api": 2
  },
  "package": {
    "file": "example.pck",
    "mode": "additive"
  },
  "entry": "res://mods/example/entry.gd",
  "dependencies": [],
  "conflicts": [],
  "load_order": 0,
  "content": {
    "index": "content_index.json",
    "overrides": {
      "characters": [],
      "upgrades": []
    }
  }
}
```

### 4.1 Identity / 身份与展示

| 字段 | 类型 | 建议约束 |
|---|---|---|
| `schema_version` | 整数，必需 | 首版固定为 2；未知版本拒载 |
| `id` | 字符串，必需 | 保留 `^[a-z0-9_]+$`；与安装目录、自身资源命名空间一致，发布后保持稳定 |
| `version` | 字符串，必需 | Mod 自身版本，用于展示、依赖判断；不表示本体兼容性 |
| `name` | 字符串，必需 | 显示名称；改名不改变 ID |
| `description` | 字符串，可选 | 默认空字符串 |
| `authors` | 字符串数组，必需 | 至少一个非空作者名；第一版不引入作者身份认证 |
| `icon` | 字符串，可选 | 包外相对路径，推荐 `icon.png`；挂载前可读取 |

字段类型错误应明确报错，不以 `str()`、`int()`、`bool()` 强制转换后继续加载。路径拒绝绝对路径、穿越和越界访问。显示文本不参与兼容判断；多语言名称、主页、许可证等扩展字段后续按实际需要增加。

### 4.2 Compatibility / 兼容性

`compatibility.game` 是本体兼容范围：`min` 包含下限，`max_exclusive` 不包含上限。建议发布包显式提供两者，构建工具不能自行填写一个宽泛上限。

本体采用四段版本号，不能直接假定符合三段 SemVer。应集中定义严格比较器，并明确可接受段数、前导 `v`、测试版后缀的含义。非法片段不能转成 0；测试版不能静默视为同号正式版。具体语法见 §11 待确认项。

`compatibility.mod_api` 声明 Mod 使用的接口契约版本，适用于整个包，不仅 entry。本体明确维护支持版本集合，不能仅根据数值较小就推断兼容。`ModAPI.VERSION` 与 `ModManager.API_VERSION` 应统一来源；支持旧版本须有回归依据。现状证据：`script/mod_api.gd:6`、`script/mod_manager.gd:19`。

涉及 `ExtensionHooks`、公开资源字段和场景结构的契约也应纳入兼容政策。对于直接依赖本体内部实现的 Mod，应收紧本体范围；不能宣称 ModAPI 版本相符就必然兼容所有内部调用。第一版暂不引入大量独立能力编号。

Godot 格式和引擎要求仍以实际 PCK 文件头检查为准；构建器版本记录在发布清单，不额外要求作者重复手写一份可能失真的引擎版本。

### 4.3 Package / 加载与覆盖

`package.file` 指向安装目录内的 PCK。`package.mode` 显式选择：

- `additive`：使用自身 `res://mods/<id>/` 命名空间，不覆盖本体或其他 Mod；必要的 Godot 导出辅助资源单独识别并验证归属。
- `override`：允许覆盖明确声明的本体资源，须额外提供 `base_contract` 和 `replace_paths`。

覆盖包的 `package` 示例：

```json
{
  "file": "example.pck",
  "mode": "override",
  "base_contract": "<目标本体发布流程生成的兼容标识>",
  "replace_paths": [
    "res://ui/round_timer.gd"
  ]
}
```

`base_contract` 独立于显示版本。初期建议严格匹配不可变的本体构建标识，之后再根据回归依据提供共享的文件契约标识。Mod 构建器从目标本体的发布元数据读取该标识；不得根据旧源码的显示版本猜测。仅用当前 Git HEAD 也不足以标识带未提交改动的产物。

`replace_paths` 是运行期允许覆盖的逻辑资源路径清单，同时参与构建检查。实际包里出现未声明的本体覆盖路径，构建和加载都失败。导出依赖不会自动获得覆盖许可；必须删除冗余依赖、调整接入方式，或对允许覆盖的依赖作显式声明。

检查必须关联原始资源路径、`.remap` 和编译产物；不能只匹配 `.gd`，也不能一律拒绝合法的 `.godot/` 导出资源。相同规则适用于 PCK 删除条目。

受保护文件至少包括所有 autoload 脚本及其场景、Mod 加载与校验代码、项目配置和全局脚本映射等启动基础文件。即使 manifest 显式声明，也拒绝覆盖。精确清单及导出映射规则在实现前确定，并以真实导出样本验证。

### 4.4 Dependencies / 依赖与冲突

建议依赖采用结构化对象：

```json
{
  "dependencies": [
    {
      "id": "shared_library",
      "version": {
        "min": "1.2.0",
        "max_exclusive": "2.0.0"
      }
    }
  ],
  "conflicts": [
    { "id": "other_mod" }
  ]
}
```

依赖版本范围可省略，表示接受该 ID 的任意合法版本；提供范围时须通过统一比较器验证。冲突对象可选附带同样的版本范围。拒绝重复依赖和自依赖；检测依赖环。

第一版只支持必需依赖，不加入可选依赖、替代提供者或自动下载。保留 `load_order` 作为同级排序提示；依赖和冲突始终优先于用户排序和数字提示。

### 4.5 Content / 内容声明

`content.index` 指向统一内容索引；角色、社团等显式条目逐步移入索引，避免 manifest 持续增加按玩法命名的顶层字段。波次配置移入内容声明，保留原有自动波次与显式波次语义。索引格式扩展需单独定义版本和测试，不借本次设计直接更改当前格式。

`content.overrides` 按 kind 分组，解决裸 ID 无法表达资源类型的问题。它仅允许注册表内容覆盖，与 `package.replace_paths` 的文件覆盖分开判断。

第一版不强制重写现有目录发现机制：构建时可从目录生成索引；发布时以已验证索引为准。声明缺失资源、类型错误、未授权 ID 覆盖等，在能够静态检查时由构建器提前报告；挂载后的内容错误不能假装可安全卸载回滚。

## 5. Release facts / 生成的发布清单

建议 `package.lock.json` 至少记录：

- 自身清单格式版本、Mod ID 与版本。
- 发布 `mod.json`、PCK、内容索引及包外功能性文件的 SHA-256 和大小。
- 实际逻辑资源目录、覆盖路径和导出映射关系。
- 构建使用的 Godot、SDK 版本及覆盖包的目标本体兼容标识。

清单不记录自身哈希，避免循环依赖。记录 PCK 整体哈希时，不将含该哈希的清单再次打入同一个 PCK。

加载器检查清单与实际文件一致，并独立检查 PCK 目录；清单不能授权核心文件覆盖。SHA-256 用于内容一致性，不证明作者身份；本方案不引入签名体系，也不把通过检查的脚本视为可信沙箱代码。

## 6. Admission / 挂载前准入流程

建议将只读检查集中到一个可测试模块，返回结构化结果：`{ok, code, details, normalized_manifest}`。模块输入显式提供目标本体版本、支持接口版本和本体兼容标识，便于安装器、启动加载器及测试复用；不自行挂载候选包。

1. 读取包外 manifest，验证 JSON、格式版本、必需字段、类型和路径。
2. 只读解析 PCK，检查格式、引擎要求、内容范围与一致性；核对发布清单。
3. 检查本体范围、Mod 接口支持、覆盖包的本体兼容标识。
4. 检查实际资源归属、受保护文件、未声明覆盖及删除条目。
5. 对全部候选包解析依赖版本、冲突和顺序；传播拒载结果。
6. 仅挂载通过准入的包，随后执行现有内容扫描、补丁和 entry 流程。

安装时在交换目录前完成校验；失败保留旧安装。启动仍需重新检查，不能因曾安装成功就跳过，否则无法覆盖本体升级或安装目录被修改的情况。依赖和跨 Mod 冲突在启动时按完整候选集合最终判定。

加载器应在候选包挂载前取得本体版本、兼容标识及校验实现，防止判断依据被候选资源覆盖。通过准入也不保证任意脚本运行正确；不支持把挂载后执行失败包装成无副作用的事务回滚。

## 7. Rejection UX / 拒载状态与提示

保持 `enabled` 表示用户意图，`mounted` 表示本次实际结果。不改写 `mods_state.json` 来表达不兼容，也不删除旧包。

管理页展示名称、版本及具体拒载原因；图标优先读包外文件，拒载包不能为展示图标而临时挂载。保留更新、卸载等操作，依赖方显示阻塞链。

建议错误码包括 `manifest_invalid`、`manifest_schema_unsupported`、`game_version_mismatch`、`mod_api_unsupported`、`base_contract_mismatch`、`protected_resource`、`undeclared_override`、`package_integrity_failed`、`dependency_incompatible`。码用于程序分支，中文或本地化提示包含要求值、实际值和相关路径。

示例：`未加载：此 Mod 要求本体 >= v0.5.1.4 且 < v0.5.2.0，当前为 v0.5.2.0。请更新 Mod。`

## 8. Migration / 旧字段迁移

| 当前字段 | v2 去向与限制 |
|---|---|
| 无 `schema_version` | 识别为旧格式；只读诊断，不默认为 v2 |
| `author` | `authors` 数组 |
| `game_version` | `compatibility.game.min`；不能自动推断兼容上限 |
| `api_version` | `compatibility.mod_api`；缺失不能填当前版本作为兼容证明 |
| `pck` | `package.file` |
| `replace_files` | `package.mode` |
| `replace_paths` | `package.replace_paths`；核对实际导出结果后才能迁移 |
| `overrides` | `content.overrides`；结合内容类型转换，歧义条目要求作者确认 |
| `characters`、`societies` | 内容索引 |
| `enemy_group`、`enemy_waves` | 内容声明，保留现有语义 |
| 字符串依赖/冲突 | 对象数组；原来未限制版本的条目继续保持不限版本 |
| `entry`、`load_order` | 保留语义，增加严格类型与路径校验 |

建议先发布校验工具与迁移诊断，再迁移官方 Mod 和示例，最后启用正式拒载规则。工具生成转换草稿及需人工确认项，不原地覆盖用户旧包。

旧格式默认可展示和诊断，正式加载需明确迁移政策。不能仅因没有 entry 就放行：场景和资源仍可关联脚本。若提供过渡白名单，应绑定已验证的具体包哈希及目标本体契约，不能对某个 Mod ID 永久放行。是否提供过渡白名单见 §11。

`enabled`、`mounted`、错误、用户排序和待卸载状态属于运行状态，继续放在用户配置或内存，不写回作者 manifest 或发布清单。

## 9. Rollout / 实施顺序

1. 定稿字段语义、版本语法、核心保护清单和旧包政策。
2. 实现 v2 严格解析与只读准入模块，将现有 PCK 检查扩展为可复用的目录信息读取。
3. 在启动挂载前接入校验，并沿依赖链传播错误；安装事务复用相同规则。
4. 更新 SDK 构建与校验工具，生成发布清单，校验最终 PCK，迁移示例及官方联机 Mod。
5. 补充管理页提示与本地化；通过真实旧包和正式导出回归后启用拒载。

现有管理页的运行期返回契约防护保留，待新机制覆盖实际发布场景后再评估简化。仅修改旧包 manifest 不能作为兼容验证。

## 10. Acceptance / 验收标准

| 场景 | 预期 |
|---|---|
| 未知格式、必需字段缺失或类型错误 | 拒载，错误明确，不执行隐式类型转换 |
| 本体处于范围下限、上限 | 下限通过，上限拒载 |
| 非法版本或未明确支持的测试版后缀 | 明确报错，不静默按正式版比较 |
| 不支持的 Mod 接口版本 | 整包拒载，不能只跳过 entry |
| 覆盖包显示版本相同但本体契约不同 | 拒载 |
| 实际 PCK 含未声明本体文件、核心 `.remap` / 编译文件或删除条目 | 构建与启动均拒绝 |
| 合法 additive 包及 Godot 导出辅助资源 | 正常通过，不误拒正常导出依赖 |
| manifest、PCK 或包外内容索引被修改 | 一致性检查失败 |
| 被依赖包不兼容或挂载失败 | 直接与传递依赖方均不生效，其他无关包继续加载 |
| 手动安装、便携目录、已有安装 | 同样执行启动准入 |
| 安装候选不兼容 | 旧安装和用户启用选择保留 |
| 无 entry、含脚本场景 | 不跳过兼容与资源检查 |
| 本机旧联机包隔离副本 | 挂载前拒载，资源视图不被修改，不复现旧签名解析错误 |
| 正常新版联机包 | 管理页、设置页、战斗及联机回归通过，不能用专项检查代替整包验证 |

测试检查拒载前后资源来源一致，并用入口、场景初始化及补丁标记证明候选代码未执行。真实包测试使用隔离目录，不修改本机安装。
